# Shinhan Super SOL development tenant

`shinhanManifest` selects the existing WSS sandbox capability baseline for signed development sessions. It is a product integration scaffold, not Shinhan-approved policy, custody, authentication, or provider configuration. Production activation needs an institution session issuer and approved native secure input.

The local UI evidence and design authority are in `ui-kit/`. Original screenshots, recordings, `app-logo.jpg`, and `splash.jpeg` stay local. The PWA and Android icons under `apps/` are resized from the supplied app logo. The photographed splash is not used because it includes system UI and a security message; the Android launch screen uses solid blue with the app mark.

- Web/PWA: `/shinhan/app` opens the Shinhan host finance root; the upper-right wallet control opens the WSS wallet at `/shinhan/wallet`. The wallet subview has no bottom host navigation.
- Android: `apps/shinhan-android` opens the same signed-session host. Its debug package ID is `com.tookwss.shinhan`.
- Local identity UI review: run `npm run dev -w @took-wss/wallet-webview` and open `http://127.0.0.1:5174/shinhan-review.html?scene=identity`. The finance → 쏠지갑 → 내 디지털 신원인증 path is a separate React-memory screen review; `identityState=issued` loads a synthetic card. It does not call the credential service. The live path is in `/shinhan/app` and `/shinhan/wallet` through the signed reference Host session.
- Live development identity: after the existing name, birth-date, and phone OTP registration, wallet creation prompts for digital ID consent. `services/institution-bff/src/digitalIdentityService.ts` reads the tenant-scoped verified profile, signs a `vc+jwt` credential with a Took development issuer DID, and records metadata only. The Host keeps the credential, a nonextractable Ed25519 holder key, and a private commitment opening in IndexedDB. The wallet WebView receives only status and display metadata through the versioned bridge. Reopening **내 디지털 신원인증** shows the card, linked wallets, and information available for verification.
- Wallet binding requires a fresh server challenge, a holder-key signature, and an EVM personal signature from the existing Host wallet approval ceremony. The BFF resolves the address from the authenticated tenant wallet and checks both signatures before recording the binding. The current binding path supports EVM externally owned addresses backed by the Host signing path; contract-wallet signatures need a separate adapter.
- The name and birth-date verification path checks the issuer signature, holder signature, one-time nonce, credential state, and an equality proof against an issuer-signed commitment. The proof package is `packages/identity-proof`. The compact credential and proof contain no raw name or birth date. The currently wired screen checks the signed-in customer's own stored values; a separate relying-party request and recipient-controlled transfer gate have not been connected. This development proof protocol needs independent cryptographic review before any production use.
- `DEV_ASSUMED` is explicit in the signed credential and `productionEligible` is false. Phone possession verifies control of the number only; entered name and birth date remain self-asserted. The service and Host vault actions are disabled in production builds. The local issuer seed lives in ignored `.env.local` as `WSS_DEV_IDENTITY_ISSUER_SEED_HEX`. After applying migrations, `npm run verify:shinhan-identity` checks the issue, proof, replay, tamper, mismatch, and binding paths with a synthetic profile that it removes afterward.
- Host-owned finance/account transfer views use synthetic values and never submit a bank transfer through WSS. The photographed simple-password keypad is represented in local preview with a tap count only. WSS authentication and signing remain host-owned.
- The wallet keeps the shared WSS capabilities for creation, recovery, holdings, activity, receive/send, exchange, payments, and connected wallet paths where their configured development providers are available. A declared module or a visible action does not prove a funded transaction or institution approval.
